01项目背景与评估方法

先固化自研架构的技术约束与上报基线，再据此定义评估维度——所有候选框架按同一把尺子打分。

1.1 自研架构约束（评估基准）

层次组成对开源框架的诉求
🔴 平台侧 · 管理层（完全自研）终端 Agent Center：WS 连接网关（控制面）+ 无状态接入层（数据面 HTTP/2 + mTLS）；安全管理中心：AI 资产发现管理 / 策略统一管理 / 安全分析可视化（MITRE ATT&CK + AI 智能体链路行为画像）/ 自动化响应不引入任何开源 Server；统一日志由 Agent Center 接入并经 Kafka 分流，安全管理中心消费分析；资产范围仅 AI 专项
🟡 终端侧 · 主程序（自研）ws 客户端 / 日志收集与上报（数据面收口）/ 插件生命周期管理宿主-子进程工程先例；IPC 消息总线契约；传输能力统一收口
🟡 终端侧 · 插件（包装开源框架）Rustinel 行为采集与检测 / AIDR AI 防护 / AV / 响应，每插件独立进程优先复用三端原生安全行为采集与检测；避免多个引擎重复订阅同一事件源
🟢 方寸 AIDR SDK 集成AI 资产发现与防护（独立插件进程形态）由主程序拉起/守护/升级；AI 资产、行为与告警经本地文件或 IPC 汇聚上报

1.2 评估维度与权重（按双平面基线重定）

权重维度说明

35%行为遥测与检测（AI 场景）权重上调：三端行为事件、规则检测、内存扫描与 AI 客户端威胁识别；通用资产与周期查询不计分

02上报架构基线：双平面设计（已定型）

日志上报不走 WebSocket 单通道。终端 Agent Center内部采用控制面/数据面分离：WS 连接网关负责实时控制，无状态接入层负责 HTTP/2 + mTLS 数据接入；安全管理中心通过 Kafka 消费数据并执行分析、策略与响应闭环。

2.1 双平面定型

平面终端 Agent Center 组件与协议设计理由
🔴 控制面WS 连接网关（WebSocket over TLS，443）：注册 / 心跳 / 策略下发 / 实时指令 / 插件管理低频小消息、需要双向实时触达；Agent Center 维护连接路由、跨节点推送和终端在线状态；告警类小消息也可走此通道保实时
🟢 数据面无状态接入层（HTTP/2 POST + mTLS，443）：终端本地 WAL、断点续传、zstd、1~4MB 批量与幂等序号；接入层完成验签、解压、去重和 topic 路由 → Kafka（遥测/告警/AI 资产/AI 链路行为）避免单通道队头阻塞；数据面无状态线性扩容、控制面按连接数扩容；安全管理中心从 Kafka 消费，与终端连接层解耦
平台两中心边界：终端 Agent Center是终端连接与数据入口，包含 WS 连接网关、无状态接入层及终端注册/在线状态/连接路由，不承载重型安全分析；安全管理中心是业务与运营中枢，负责 AI 资产、策略、ATT&CK 分析可视化、AI 智能体链路行为画像和自动化响应。两中心通过 Kafka 数据流与控制指令 API 协作，避免海量终端连接状态与分析服务相互耦合。

2.2 数据面关键设计点

  • 本地磁盘 WAL 先行：断网期间数据持续落盘，重连后按幂等序号（batch seq）续传去重——断网不丢语义由主程序统一保障
  • zstd 压缩 + 1~4MB 批量：遥测压缩比通常 10:1；批量大小平衡时延与请求开销
  • 分级传输：已落盘告警（传输不丢、秒级，可走 ws）/ 行为遥测流（可延迟、可降级采样）/ AI 资产快照（低频全量+增量）——服务端按 topic 分流
  • 容量测算（仅全量遥测增强模式，10 万终端示例）：若 fork 开启日均 50MB/端原始遥测，压缩后约 6MB/s 均值、峰值 ×10；默认 Rustinel 告警模式远低于此量级。行业参考：osquery logger_tls 与 Elastic Agent→Fleet 批量模式
基线对评估逻辑的反转：WAL/zstd/mTLS/重传全部收口在自研主程序——框架只需「把数据交出来」（本地文件或标准批量端点），不需要自带可靠传输。自带 gRPC/私有协议的框架（Elkeid/Wazuh/Velociraptor）数据面反而成了负资产；纯本地输出的框架（Rustinel/osquery filesystem logger）与收口型模式天然契合。

4.1 候选框架日志收集方式横向对比

六个切面：采集模型、端上归一化、本地落盘形态、上报通道、断网缓冲、丢弃语义。这张表直接支撑落地方案的两个设计：Supervisor 文件采集器（三种读取模式）与「传输收口在主程序、插件不自带可靠传输」的基线。
框架采集模型端上归一化本地落盘形态上报通道断网缓冲丢弃语义
osquery pull：周期 SQL 查询（schedule）+ 差分日志；事件表（Windows Event Log 订阅等）为辅 查询结果集 JSON 行（列名即字段，schema 随查询变化） filesystem logger：results.log 本地追加文件 文件由外部搬运（Filebeat 等）或 logger_tls（HTTPS 批量） TLS 模式内存缓冲 + 退避重试；文件模式天然持久 缓冲超限丢弃并计数；无检测，无检测前丢弃概念
Rustinel push：实时传感器流（ETW 双会话 + Event Log / eBPF / ES+BPF），事件驱动 Sysmon 风格字段 → ECS NDJSON，三端统一 四类本地文件：alerts.json.<date>（追加）、rustinel.log.<date>、telemetry.json（30s 整写快照）、heartbeat.json.<date>（追加）；另有 capture 回放录制 默认本地文件由外部收口（本设计）；可选 webhook（HMAC 签名 + 退避重试 + Retry-After） 文件即持久缓冲；64MB 告警字节预算，超限丢文件副本保 webhook 六条有界通道满载丢弃并逐通道计数（telemetry.json 30s + 限频 loss 告警）

Wazuh push：logcollector（文件/syslog/Event Log 通道）+ syscheck FIM（实时+周期）+ rootcheck/SCA 周期扫描 + 库存模块 端上仅做初步解析，解码与富化在 Manager（decoders） 端上无标准格式本地输出（alerts 在 Manager 侧生成） AES 加密私有 TCP 1514 直发 Manager agent 内存 counter 队列，非持久 WAL 队列满丢弃，端上计数能力弱，平台不可见

对接面官网 + 源码 v1.11.0 双重校准后的评估详情
版本与许可源码 Cargo.toml 声明 version = "1.11.0"、license = "Apache-2.0"、rust-version = "1.98"；release profile 使用 panic = "abort"——崩溃即进程退出、不做栈展开，Supervisor 必须具备看门狗、快速重启与崩溃计数上报
Windows 采集（P0）ETW + Windows Event Log，用户态无自研驱动；覆盖进程、镜像加载、网络、文件、注册表、DNS、PowerShell、WMI、服务、计划任务与 Security 审计。支持 Windows 服务安装/启动/停止/卸载，官方标记 Stable（Windows 10/11、Server 2016+），是三端中覆盖最完整的平台

数据面（20%）4/5 · 官方默认将告警追加到 alerts.json.<date>（ECS NDJSON、按 UTC 日期轮转），运行日志写 rustinel.log.<date>；可选 webhook 在本项目关闭，由 Supervisor tail 收口。capture/replay 记录的是归一化后的 canonical events（命令行为、文件路径、目标地址、用户名），不是原始 ETW/eBPF/ESF 载荷，也不是告警输出，属于规则回归测试工作流，不等于生产持续原始遥测输出；全量行为检索需 fork 扩展
控制面（10%）3/5 · Sigma/YARA/IOC 与响应配置支持本地热重载：若规则文件存在但全部编译失败，则拒绝本次重载并保留旧引擎，部分失败则加载可用规则，成功后通过 ArcSwap 原子切换；debounce 默认 2000ms（源码钳制下限 100ms），兜底轮询 60s。Supervisor 经 ws 接收策略后写本地目录并核验生效状态
插件进程化（5%）2/5 · 单体引擎无内部插件机制，但可被 Supervisor 整体作为独立进程纳管；README 明确边界 no anti-tamper、no pre-execution blocking、no management console，由自研平台补齐

主动响应边界本地阈值响应：channel_capacity = 128、min_severity = "critical"、prevention_enabled = false（默认即 dry-run）；保护 pid ≤ 4 与自身 pid，支持镜像/路径 allowlist。三端实现：Linux pidfd_open + pidfd_send_signal(SIGKILL)、Windows OpenProcess + TerminateProcess、macOS kill(pid, SIGKILL)（源码注释明确存在 PID 复用竞态）——即 macOS 并非「仅检测」。无平台化响应编排，隔离/文件处置/审计闭环由自研响应动作插件承担

5.2.1 Windows ETW 已知盲区（PoC 必测）

盲区 / 限制对检测与平台建设的影响
哈希延迟与镜像加载无哈希ETW 不直接提供 Hashes/Imphash；可执行文件哈希事后计算并延迟匹配，针对的是计算时的文件状态；镜像加载事件无哈希，相关规则不可依赖
注入类遥测缺口无 CreateRemoteThread、ProcessAccess、Named Pipe、Driver Load 等等价事件；涉及注入的规则即使加载也可能永远不触发，AI 客户端注入检测不能仅依赖 Rustinel
命令行事后回填Kernel-Process 事件不携带 CommandLine，需要查询仍存活进程，存在短进程退出竞态；应实测缺失率而非按 100% 设计
部分字段不可填充CurrentDirectory、部分镜像加载/计划任务 User、Signed、TaskContent 等存在空值；Sigma 规则上线前用 sigma doctor 和字段覆盖报告剔除不可触发规则
文件路径学习缺口启动前已经打开句柄的文件写入可能无法解析路径；高频文件检测需评估启动基线学习与路径解析时延
PowerShell / 审计配置依赖相关 Provider 覆盖 Windows PowerShell 5.1，不覆盖 PowerShell 7；Module Logging、Security Audit Subcategory、对象 SACL 等主机配置缺失时，订阅成功也不代表有事件
无企业级自保护高权限攻击者可停止 ETW Trace 或终止 Agent；需 Supervisor 心跳、服务恢复、进程完整性校验和平台离线告警补偿，但不能宣称等同内核防篡改

录制与回放src/capture/：记录归一化后的 canonical events（命令行为、文件路径、目标地址、用户名），双文件结构（NDJSON payload + CaptureManifest sidecar），可跨平台回放；文件 owner-only 权限并与告警/运行日志分开存放。→ 不是原始 ETW/eBPF/ESF 载荷，也不能作为生产原始遥测输出

5.4 Wazuh 排除定案

对接面评估详情（官方组件文档 + 端口基线校准）
产品定位Wazuh 是「自建 SOC 平台」，不是「终端 EDR Agent」：Agent + Server + Indexer + Dashboard 四组件构成 SIEM + XDR 闭环，检测结论由 Server 侧分析引擎（decoders → rules）产生，Agent 只负责采集与本地响应执行。能力越完整，能被单独摘出来当终端插件的部分就越少——这才是它得 2.55 分的原因，而不是「产品能力弱」
数据面（20%）1/5 · Agent→Manager 私有 TCP 1514（默认 TCP、可选 UDP，AES 加密）——六框架中唯一既无 HTTP 端点、也无本地标准格式输出；agent 缓冲为内存 counter 上限（非持久 WAL）。对接唯一路径=重写 C 传输层 → 触发 GPLv2 修改义务
控制面（10%）2/5 · 注册（1515 TLS 认证并下发唯一密钥）/ 指令 / agent group 集中配置体系完整，但全部锁死在 Manager 私有协议上；55000 是平台管理 API（HTTPS），不是终端控制面；引入 Manager 又与自研平台职责重叠
插件进程化（5%）1/5 · 模块以 wmodules 共享库编译内联，非独立进程；进程化改造等于另写一个 agent
跨平台（15%）4/5 · Wazuh 真正的强项：单一 Agent 覆盖 Windows / macOS / Linux / Solaris / HP-UX / AIX，六候选中平台矩阵最宽。但「跨平台」≠「行为遥测深度」——Windows 侧以 Event Log 为主，缺 ETW 进程级行为遥测等价能力；Linux 侧不以 eBPF 为核心
许可（10%）2/5 · 混合许可：Agent / Server / Ruleset 为 GPLv2，Indexer / Dashboard 为 Apache-2.0（OpenSearch 系）。GPLv2 无网络条款，纯 SaaS 侧不触发，比 AGPLv3 温和；但随安装包分发 agent 即须提供对应源码及修改，与「主程序闭源 + 零源码依赖」的交付纪律冲突。5.0 起新分析 engine 转为 AGPLv3（独立 LICENSE-engine），若未来采用其服务端能力，网络提供服务亦将触发开源义务——风险单向上升
六大能力模块入侵检测 IDS（签名 + 行为，含隐藏进程 / Rootkit / 无文件）、日志分析、FIM、漏洞检测 VD、配置评估 SCA（600+ CIS/DISA/STIG）、主动响应 AR——逐项映射见 5.4.2：五项属平台能力，仅 AR 执行侧与 FIM 采集侧触及终端
残余价值① 规则 / 解码器生态（7000+ 规则、MITRE ATT&CK 映射）→ 平台侧分析规则设计语料；② Active Response 三段式（触发→执行→回传）→ 自研响应动作框架范式；③ SCA 基线包结构 → P2 合规能力可选参考。全部为零代码引入
结论：Wazuh 的能力清单在六个候选中最完整，但完整度全部长在被自研平台替代的 Manager / Indexer / Dashboard 侧：终端侧三项对接面（数据面 1、控制面 2、插件进程 1）全部不可用，加权后仅 2.55 分。排除定案——本项目需要的是一个能被 Supervisor 纳管的终端行为采集与检测进程，而 Wazuh 要求的是放弃自研平台、直接采用它的整套 SOC。部署 Wazuh 的实质是「再建一套安全管理中心」，与既定路线重复建设。

错位点：六项能力里没有一项是「终端本地实时行为检测 + 进程级响应」的组合。Rustinel 用单进程 + 本地 Sigma/YARA/IOC 就覆盖了这块；Wazuh 需要整套四组件平台才能给出同样结论。这就是「平台完整度」与「终端适配度」的错位——评分衡量的是后者。
版本演进观察（不改变本期结论）：Wazuh 5.0 的公开设计说明显示，Manager 与 Agent 进程将彻底分离（移除 Agent ID 000），以 Universal Dictionary 做类 ECS / OCSF 的字段归一，漏洞检测改由 Indexer 统一裁决，同时新分析 engine 转为 AGPLv3。对项目的三点含义：① 归一化若最终沉淀为公开 schema，可作自研 ECS 字段映射的交叉校验语料；② 但传输仍是私有协议、engine 许可更严，终端对接门槛不降反升；③ 5.0 尚处 RC 阶段，不作为选型依据，仅列入长期观察项——若其未来开放标准 HTTP 端点且许可回调，再重新评估。

5.5 Velociraptor 独立取证工具

对接面评估详情
数据面（20%）2/5 · client↔server gRPC + mTLS 深度耦合（安全模型与传输一体，不可换装）；离线收集器的本地文件模式是一次性取证场景，非常驻上报通道

5.6 OpenEDR 排除定案

对接面评估详情
数据面（20%）2/5 · 本地事件文件→Filebeat→Elasticsearch 的文件模式存在，理论上可由自研 uploader 替代——但输出格式私有（无 ECS/Sysmon 风格归一化），对接价值低于 Rustinel 同类模式

结论：文件输出模式与 Rustinel 同型但全面劣于后者（许可、归一化、维护）。排除定案。

告警字节预算与降级顺序64MB 字节预算下「丢文件副本、保摄入与 webhook」——给出了输出侧降级优先级的现成范式：先牺牲可重建的本地副本，再牺牲投递，绝不阻塞检测热路径
webhook 稳定投递 ID + HMAC 签名x-rustinel-delivery 在重试期保持不变 → 自研上传器幂等键设计参考；x-rustinel-signature = sha256=HMAC(secret, "<timestamp>.<body>") → 平台侧验签与防重放可直接对齐；Retry-After 上限钳制 → 退避策略不应无限增长
ETW 双会话分级 flush主会话 20ms 可让步，进程会话 5ms 在队列压力下仍保持 flush——「关键事件优先保时效、非关键事件可让步」的分级策略，可直接移植到自研采集插件的资源竞争处理
规则全坏拒绝重载 + ArcSwap「找到文件但全部编译失败 → 拒绝本次重载并保留旧引擎」是策略下发的正确失败语义；ArcSwap 提供读侧无锁的原子切换实现范式。自研策略下发必须复制这两条，而不是「加载失败即清空」

去重 rollup 的 event.count 语义首条即时发出、rollup 携带被抑制次数 → 平台侧统计真实事件量必须 sum(event.count 缺失记 1)，否则告警量被严重低估；该口径应写入自研 schema 规范

10.1 选型理由（三条主轴）

  • 主轴一 · Agent 类型匹配优先：osquery 的核心是端点状态 SQL 查询，适合资产、配置与合规，不是实时行为检测和响应 Agent；保留 3.85 分是为了客观呈现接口与工程优势，但高分不能弥补产品类型不匹配，因此最终方案不采用。
  • 主轴二 · 单引擎采集检测闭环：Rustinel 同时具备原生行为采集、Sigma/YARA/IOC 端点检测和 ECS 告警落盘；异步管线、规则预编译、源头降噪和后台扫描适合高负载终端，与 Supervisor 收口组合后可替代 osquery 采集 + 独立检测引擎路线。
  • 主轴三 · AI 专项职责独立：AIDR SDK 负责 AI 资产与行为防护，不承担通用终端行为遥测；AV 负责已知威胁查杀，响应插件负责处置，避免职责混叠。v4.0：两者与统一客户端的集成形态已定型为独立适配进程（宿主不加载 SDK），见《统一客户端第三方插件 SDK 集成设计方案 v1.2》——含 plugin_config 声明式配置、ZIP 验签安装、GUI 状态卡融合与指令通道。
  • 主轴四 · 协议与许可负资产化：Wazuh、Elkeid、Velociraptor 的私有或 gRPC 通道无法复用到双平面基线，且 GPL/AGPL 增加闭源商业分发风险，因此只保留语料、设计或独立工具价值。
